# 数据库初始化与升级

所有命令从 `governance-suite` 根目录执行。以下是操作指南，本次文档整理没有执行 SQL。目标环境遵循[单实例规范](AGENTS.md#部署范围单实例)。

## 新环境初始化

[init-databases.sql](init-databases.sql) 是基础建表脚本，创建 `governance` 和 `doctor_assistant`，包含普通 `CREATE TABLE`，不能在已有业务表上反复执行。它也不是完整的增量迁移器。

仅在确认目标为空库后执行，连接参数替换为目标环境，密码交互输入：

```bash
mysql -h127.0.0.1 -P3306 -uroot -p < ai/init-databases.sql
```

执行基础脚本后，按启用模块核对下表中的结构差异。尤其向量生命周期字段和事件表需要额外迁移，不能仅凭基础脚本执行成功就启动全部功能。

| 模块 | 结构来源与注意事项 |
| --- | --- |
| 聊天 | 基础脚本包含会话归属与随访历史字段；已有库参照下节迁移 |
| 画像 | 以 `user-profile-service/src/main/resources/mapper/` 引用的表与列核对基础脚本；新增审核或死信治理能力另核对相应 SQL |
| 向量记忆 | [migration 目录](vector-memory-service/src/main/resources/db/migration/)；V4/V5 的部分内容已在基础脚本中，V6 增加生命周期字段，V7 增加摘要关联字段，V8 创建生命周期事件表 |
| 医生助手 | [schema.sql](doctor-assistant-agent/sql/schema.sql) 为模块建表入口；与总脚本存在重叠，选择一种基础来源后核对 [migrations](doctor-assistant-agent/sql/migrations/) 中的审计、上下文、运行策略、结果归因和会话关联结构 |
| 知识库 | [init_kb_service.sql](knowledge-base-service/src/main/resources/db/init_kb_service.sql) 为模块参考；`CREATE TABLE IF NOT EXISTS` 不会为旧表补字段 |
| 评测 | 使用本地文件存储，不需要上述业务库 |

当前模块 POM 未声明 Flyway/Liquibase 迁移依赖，不能因为 SQL 位于 `db/migration/` 就假定服务启动会自动执行。迁移前核对实际列、索引和已应用记录；含 `ADD COLUMN` 的脚本不能盲目重放。

## 已有环境升级

保留已有数据，停止相关服务写入，备份并核对实际结构，再只应用缺失迁移。单实例升级先停旧进程，完成结构检查后再启动新进程。升级失败时按实际已执行步骤恢复，不能用删除共享数据库代替迁移。

患者会话归属相关升级按以下依赖顺序检查，已具备的结构跳过相应建表或加列步骤：

1. [随访提醒建表](doctor-assistant-agent/sql/migrations/2026-11-23-high-risk-follow-up.sql)：作用于 `doctor_assistant`。
2. [医生端会话关联](doctor-assistant-agent/sql/migrations/2026-11-23-patient-conversation.sql)：补会话关联并为后续归属回填提供来源。
3. [聊天端会话归属](ai-chat-service/sql/migrations/2026-11-23-conversation-owner.sql)：迁移账号需读取两个库；聊天运行时仅使用本库归属记录。
4. [随访问答历史](ai-chat-service/sql/migrations/2026-11-25-follow-up-chat-history.sql)：作用于 `governance`，支持同轮重试更新与确认状态。

归属回填来自聊天历史和医生端可追溯任务，同一会话有多个主体时锁定编号。旧版仅在 Redis 中的上下文只允许原主体恢复，无法验证的匿名会话重新开始。身份和接口契约见[聊天服务说明](ai-chat-service/README.md#患者聊天入口与会话归属)。

向量记忆已有库按 V4～V8 的结构依赖核对，完整生命周期能力要求 V6、V7、V8 对应列与表存在。代码实现情况见[生命周期说明](vector-memory-service/docs/向量记忆分类与生命周期.md)。

## 基础脚本中的数据库和表

### governance
- **使用服务**包括 user-profile-service、vector-memory-service、ai-chat-service 和 knowledge-base-service。
- **表结构**:

#### 用户画像 (user-profile-service)
  - `t_customer` - 客户基础档案
  - `t_health_assessment` - 健康评估
  - `b_ai_user_memory` - 用户记忆
  - `b_user_profile_behavior_preference` - 行为偏好
  - `b_user_profile_candidate_field` - 候选字段
  - `b_user_profile_field_conflict` - 字段冲突

#### 向量记忆 (vector-memory-service)
  - `b_ai_group_memory` - 群体记忆
  - `b_ai_group_memory_candidate` - 群体记忆候选
  - `b_ai_group_memory_conflict` - 群体记忆冲突
  - `b_ai_group_memory_review_audit` - 群体记忆审核日志

#### 对话服务 (ai-chat-service)
  - `t_ai_chat_history` - 对话历史
  - `ai_chat_conversation_owner` - 会话归属

#### 知识库 (knowledge-base-service)
  - `knowledge_base` - 知识库
  - `knowledge_document` - 知识文档
  - `knowledge_document_chunk` - 文档分块
  - `knowledge_document_parse_result` - 文档解析结果

### doctor_assistant
- **使用服务**: doctor-assistant-agent
- **表结构**:
  - `agent_execution_log` - Agent 执行日志
  - `agent_pending_task` - Agent 待处理任务
  - `agent_follow_up_reminder` - 高风险随访请求去重与患者站内收件箱，投递时间在审批事务中写入
  - `agent_session` - Agent 会话
  - `chat_message` - 对话消息
  - `follow_up_task` - 随访任务
  - `health_knowledge` - 健康知识
  - `patient_profile` - 患者档案
  - `prescription_record` - 处方记录
  - `weight_record` - 体重记录

此清单描述基础脚本，不代表所有模块的最终表结构。迁移还可能增加生命周期事件、运行策略与归因等表。

## 存储职责

`governance` 由画像、向量记忆、聊天和知识库共享，修改或重建会影响多个服务。MySQL 不仅存元数据，也保存画像、记忆正文、历史和治理记录；Milvus 保存向量及检索载荷；Redis 保存会话、缓存和索引辅助状态。

聊天历史保存在 `t_ai_chat_history`。普通路径可通过 RabbitMQ 同步到 Elasticsearch 的 `chat_history` 索引；高风险随访问答直接保存数据库历史，不触发该索引同步或长期记忆提取。

## Milvus 实际 collection

当前自定义 [MilvusVectorStoreConfig](vector-memory-service/src/main/java/com/lx/governance/vectormemory/config/MilvusVectorStoreConfig.java) 创建：

| Bean | collection |
| --- | --- |
| `userMemoryVectorStore` | `ai_user_memories` |
| `groupMemoryVectorStore` | `ai_group_memories` |

[VectorStoreService](vector-memory-service/src/main/java/com/lx/governance/vectormemory/integration/storage/VectorStoreService.java) 注入 `userMemoryVectorStore`。`application.yml` 中虽保留 `collection-name: user_memory_vectors_v3`，上述自定义 Bean 并不使用该值命名；排查时以实际注入和连接的 collection 为准，不能照旧文档查 `user_memory_vectors` 或 `group_memory_vectors`。

当前配置维度为 1024，须与实际 Embedding 输出一致。`milvus.reset-collections-on-startup` 默认关闭；开启会触发删除已有 collection 的逻辑，不用于常规启动或数据库升级。知识库维护自己的 collection 配置，不能与记忆服务混用。

## 完成检查

- 目标库、表、列、索引与启用功能匹配，迁移执行记录可追溯。
- 身份归属与历史保留符合预期，使用合成数据验证升级后的接口。
- MySQL、Redis、Milvus、RabbitMQ、Elasticsearch 分别验证；SQL 执行成功不能代替整个链路验证。
- 环境重置涉及数据删除，需单独授权并确认影响范围；本指南不提供默认删库步骤。
