# 医生助手 Agent 流式链路架构说明

本文档说明 `doctor-assistant-agent` 当前采用的双层流式链路实现，重点描述后端如何同时输出：

- DeepSeek 模型增量 `delta`
- ReAct 严格 JSON 解析后的结构化事件

该链路对应的主入口是：

- `POST /api/agent/execute`
- `POST /api/agent/resume`

两者都返回 `text/event-stream`。

## 1. 改造目标

原始实现是同步 ReAct：

1. 一次性调用模型
2. 拿到完整 JSON
3. 解析 `thinking/action/finalAnswer`
4. 执行 tool
5. 返回最终 `AgentResult`

这种实现只适合“完成后返回”，前端无法看到执行过程。

当前改造目标是：

1. 保持 ReAct 严格 JSON 协议不变
2. 让前端在模型生成期间就能收到增量输出
3. 在 JSON 完整收敛后继续沿用既有 `tool`、`approval`、`finalAnswer` 逻辑
4. 不把未闭合 JSON 直接当成可执行指令

## 2. 总体设计

当前链路分两层：

### 第一层：模型增量层

由 `DeepSeekClient.chatStream(...)` 负责。

职责：

1. 调用 `chatModel.stream(prompt)`
2. 逐段接收 DeepSeek 返回的文本增量
3. 每收到一个增量就回调 `deltaSink`
4. 同时在服务端拼接完整响应文本
5. 流结束后返回完整 `DeepSeekResponse`

这一层解决的是“文本实时性”。

### 第二层：结构化事件层

由 `ReActAgentEngine.requestThoughtResultStream(...)` 和 `executeStream(...)` 负责。

职责：

1. 接收模型增量并转成 `thinking_delta` SSE 事件
2. 等完整 JSON 收齐后再调用 `ReActResponseParser`
3. 解析出 `ThoughtResult`
4. 再继续发：
   - `thought`
   - `action`
   - `observation`
   - `pending_approval`
   - `final_answer`
   - `error`
   - `done`

这一层解决的是“协议安全性”和“执行驱动”。

## 3. 为什么要同时保留 delta 和 JSON 事件

原因很直接：

- `delta` 适合前端实时展示
- 结构化 JSON 适合后端安全执行

如果只保留 `delta`：

- 前端体验好
- 但后端无法在 JSON 未闭合时安全判断 `action.toolName` 和 `action.input`

如果只保留结构化事件：

- 后端执行稳定
- 但前端只能看到步骤级输出，看不到生成过程

所以当前方案是：

1. 模型输出时持续发 `thinking_delta`
2. JSON 完整解析后再发正式结构化事件

## 4. 关键类职责

### `DeepSeekClient`

位置：
[DeepSeekClient.java](src/main/java/com/health/agent/client/DeepSeekClient.java)

当前同时支持：

- `chat(...)`
  - 同步一次性调用
- `chatStream(...)`
  - 流式增量调用

`chatStream(...)` 的核心行为：

1. 构造 `Prompt`
2. 调用 `chatModel.stream(prompt)`
3. 对每个 `ChatResponse` 提取 `content`
4. 追加到 `StringBuilder`
5. 回调 `deltaSink.accept(delta)`
6. `collectList().block()` 等待流结束
7. 返回聚合后的完整 `DeepSeekResponse`

### `ReActAgentEngine`

位置：
[ReActAgentEngine.java](src/main/java/com/health/agent/engine/ReActAgentEngine.java)

新增的流式职责：

- `executeStream(...)`
- `resumeStream(...)`
- `requestThoughtResultStream(...)`

`requestThoughtResultStream(...)` 的关键逻辑：

1. 调 `deepSeekClient.chatStream(...)`
2. 每次 `delta` 到来时发 `THINKING_DELTA`
3. 流结束后拿完整文本
4. 调 `responseParser.parse(...)`
5. 返回 `ParsedThought`

### `AgentController`

位置：
[AgentController.java](src/main/java/com/health/agent/controller/AgentController.java)

当前 `execute` 和 `resume` 已切到 `SseEmitter`。

controller 只做两件事：

1. 创建 `SseEmitter`
2. 把引擎事件转成 SSE `event + data`

## 5. 当前事件模型

位置：
[AgentStreamEventType.java](src/main/java/com/health/agent/model/AgentStreamEventType.java)

### 增量事件

- `THINKING_DELTA`

### 结构化事件

- `THOUGHT`
- `ACTION`
- `OBSERVATION`
- `PENDING_APPROVAL`
- `FINAL_ANSWER`
- `ERROR`
- `DONE`

SSE 事件名会被转成小写：

- `thinking_delta`
- `thought`
- `action`
- `observation`
- `pending_approval`
- `final_answer`
- `error`
- `done`

## 6. 一次正常执行的时序

典型顺序如下：

1. 模型开始生成 JSON
2. 后端连续收到 chunk
3. 每个 chunk 触发一个 `thinking_delta`
4. 模型完整输出当前 step 的 JSON
5. 后端解析 JSON，发 `thought`
6. 如果 `finished=false`，发 `action`
7. 执行工具
8. 发 `observation`
9. 下一轮再次进入模型流式生成
10. 最终发 `final_answer`
11. 发 `done`

前端看到的事件序列可能是：

```text
thinking_delta
thinking_delta
thought
action
observation
thinking_delta
thought
final_answer
done
```

## 7. 为什么 `thinking_delta` 当前是原始 JSON 片段

这是当前实现的刻意取舍。

原因：

1. 模型协议本身要求输出严格 JSON
2. 在 JSON 未闭合前，后端无法稳定抽出完整 `thinking` 字段
3. 第一版优先打通“真实流式 + 安全解析”

因此当前 `thinking_delta` 推送的是模型原始输出增量，而不是已经抽取好的自然语言推理文本。

这意味着：

- 后端执行是安全的
- 前端可以实时看到生成过程
- 但前端如果想只显示自然语言 thought，需要自行隐藏 JSON 外壳，或等待后续服务端做增量字段提取

## 8. 审批链路在流式模式下的语义

`pending_approval` 的语义是：

1. 发出 `pending_approval`
2. 当前 SSE 流立即结束
3. 医生审批后调用 `/api/agent/resume`
4. 新开一条流继续执行

这里不保持长连接等待审批，原因是：

- 连接生命周期过长
- 资源占用高
- 与既有 `resume` 模型冲突

## 9. 与同步链路的关系

当前同步方法仍然保留：

- `execute(...)`
- `resume(...)`

用途主要是：

- 兼容现有单元测试
- 保留非流式内部调用能力

主 HTTP 入口已经切换到流式 `SSE`。

## 10. 当前限制

### 1. `thinking_delta` 仍是原始 JSON

前端直接展示时不够友好。

### 2. 结构化事件仍然只能在完整 JSON 后发出

这是协议安全要求，不是缺陷。

### 3. 纠偏重试期间也会产生新的 `thinking_delta`

如果模型第一次输出不合法，重试流里会继续往前端发增量。前端如需区分“正式输出”和“纠偏输出”，还需要额外事件字段。

## 11. 后续可扩展方向

### 方向 1：服务端提取自然语言 thinking 增量

目标：

- 继续保留 JSON 协议
- 但前端看到的是更像 Codex 的自然语言推理流

### 方向 2：新增 `raw_json_delta`

把“给人看”的 `thinking_delta` 和“调试用”的原始 JSON 流分开。

### 方向 3：给事件补 `phase` 或 `sub_agent` 分组

可以把工具调用按：

- 数据获取
- 分析
- 随访动作
- 审批

分组给前端展示。

## 12. 调试方式

最直接的方式是用 `curl -N`：

```bash
curl -N -X POST "http://localhost:8088/api/agent/execute" \
  -H "Content-Type: application/json" \
  -H "Accept: text/event-stream" \
  -d '{
    "goal": "患者最近两周体重不下降，帮我判断是否进入平台期并给出下一步建议",
    "customerId": "C001",
    "doctorId": "D001"
  }'
```

如果链路正常，会先看到 `thinking_delta`，然后再看到结构化事件。
