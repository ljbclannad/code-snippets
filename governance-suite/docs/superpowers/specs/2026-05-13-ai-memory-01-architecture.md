# AI 记忆功能设计文档 - 第一部分：整体架构

## 文档信息

- **创建日期**: 2026-05-13
- **项目**: governance-suite
- **功能**: AI 聊天用户记忆功能
- **文档版本**: 1.0

## 一、项目背景

当前 AI 聊天系统通过 Dify API 提供服务，但 AI 无法感知用户的历史数据和个人档案，导致每次对话都需要用户重复说明基本信息，用户体验较差。

## 二、目标

实现 AI 对用户的记忆功能，包括：
- **会话上下文记忆**：AI 能记住当前对话中的历史消息
- **长期用户档案**：AI 能记住用户的基本信息和历史数据，跨会话使用

## 三、核心需求

1. 用户记忆分为全局记忆（用户维度）和群组记忆（用户+群组维度）
2. 记忆来源包括：现有数据库的结构化数据 + 对话中实时提取的信息
3. 全局记忆每次都加载，群组记忆按需检索
4. 从对话中提取的信息实时保存

## 四、服务划分

我们将创建三个新的微服务模块：

### 4.1 user-profile-service (端口 8101)

**职责**：构建用户全局画像

**数据来源**：
- Customer 基础信息
- 健康评估数据
- 行为偏好（打卡、饮食、运动）
- 用户全局记忆表

**对外接口**：
- 通过 RabbitMQ 响应用户画像请求
- REST API 提供画像查询（可选）

**技术特点**：
- 使用 Spring Cache + Redis 缓存（5分钟 TTL）
- 查询多个数据源并聚合
- 序列化为 JSON 格式

### 4.2 vector-memory-service (端口 8102)

**职责**：向量存储、语义检索、记忆提取

**核心功能**：
1. **向量检索**：根据用户问题检索相关记忆
2. **记忆保存**：将提取的信息保存到 Milvus 和 MySQL
3. **记忆提取**：调用 DeepSeek API 从对话中提取关键信息

**对外接口**：
- 通过 RabbitMQ 响应检索请求
- 通过 RabbitMQ 处理提取任务（异步）
- REST API 提供记忆管理（可选）

**技术特点**：
- 使用 Spring AI 集成 Milvus
- 使用阿里云通义千问 Embedding API
- 使用 DeepSeek API 进行信息提取
- MySQL + Milvus 双写保证数据完整性

### 4.3 ai-chat-service (端口 8103)

**职责**：AI 聊天流程协调、Dify API 调用

**核心流程**：
1. 接收用户聊天请求
2. 通过 MQ 获取用户画像
3. 通过 MQ 获取群组记忆
4. 调用 Dify API
5. 返回结果给用户
6. 异步触发记忆提取

**对外接口**：
- REST API 提供聊天接口
- REST API 提供聊天历史查询

**技术特点**：
- 使用 RabbitMQ 实现请求-响应模式
- 使用 RestClient 调用 Dify API
- 异步触发记忆提取，不阻塞主流程

## 六、消息队列设计

### 6.1 Exchange 和 Queue 定义

**用户画像服务**
```
Exchange: user.profile.exchange (Direct)
  - Queue: user.profile.request
  - Queue: user.profile.response.{correlationId} (临时队列)
```

**向量记忆服务**
```
Exchange: vector.memory.exchange (Direct)
  - Queue: vector.memory.request
  - Queue: vector.memory.response.{correlationId} (临时队列)
  - Queue: memory.extraction.request (异步队列)
```

**死信队列**
```
Exchange: dlx.exchange (Fanout)
  - Queue: dlx.queue
```

### 6.2 消息格式

所有消息包含以下字段：
- `correlationId`：用于关联请求和响应
- `timestamp`：用于超时判断
- 响应消息包含 `success` 标志和 `errorMessage`

### 6.3 请求-响应模式

1. 请求方生成 `correlationId`
2. 请求方创建临时响应队列（或使用固定队列 + correlationId 过滤）
3. 请求方发送消息到请求队列，包含 `replyTo` 和 `correlationId`
4. 服务方消费请求，处理后发送响应到 `replyTo` 队列
5. 请求方根据 `correlationId` 匹配响应
6. 超时机制：5秒未收到响应则超时

## 七、数据分层

### 第一层：全局用户画像（结构化数据）

- **存储位置**：MySQL 现有表
- **数据来源**：实时查询
- **传输方式**：序列化为 JSON，通过 MQ 传递
- **包含内容**：
  - 基础信息：姓名、年龄、性别、联系方式
  - 健康评估：BMI、血压、血糖、体检结果
  - 行为偏好：饮食偏好、运动习惯、打卡记录统计
  - 全局记忆：过敏史、慢性病、用药信息等

### 第二层：群组记忆（半结构化数据）

- **存储位置**：Milvus（向量） + MySQL（备份）
- **数据来源**：从对话中实时提取
- **传输方式**：根据用户问题语义检索 Top-K 相关片段，通过 MQ 传递
- **包含内容**：
  - 症状描述："用户提到胃部不适"
  - 用药信息："正在服用XX药物"
  - 过敏史："对青霉素过敏"
  - 饮食禁忌："不吃海鲜"
  - 治疗方案："医生建议地中海饮食"

### 第三层：会话历史（非结构化数据）

- **存储位置**：Dify 平台（通过 conversation_id 管理）
- **数据来源**：当前会话的完整对话
- **传输方式**：Dify 自动管理，无需手动传入
- **包含内容**：当前会话的所有消息记录

## 八、技术选型

| 组件 | 技术选型 | 说明 |
|------|---------|------|
| 向量数据库 | Milvus | 生产级方案，需要 etcd 和 MinIO |
| Embedding 模型 | 阿里云通义千问 API | 1024 维，按调用次数收费 |
| 信息提取模型 | DeepSeek API | 成本低，速度快，支持 JSON 模式 |
| AI 集成框架 | Spring AI | 统一抽象，简化开发 |
| 消息队列 | RabbitMQ | 已有基础设施 |
| 缓存 | Redis + Spring Cache | 已有基础设施 |
| 服务注册 | Nacos | 已有基础设施 |

## 九、非功能性需求

### 9.1 性能要求

- 用户画像查询：< 100ms（缓存命中）/ < 500ms（缓存未命中）
- 向量检索：< 200ms
- 完整聊天流程：< 3s（不含 Dify API 时间）
- 记忆提取：异步处理，不影响主流程

### 9.2 可用性要求

- 服务可用性：99.9%
- 降级策略：
  - 用户画像超时：返回空画像，继续流程
  - 向量检索超时：返回空记忆列表，继续流程
  - Dify API 超时：返回错误给用户
  - 记忆提取失败：记录日志，不影响主流程

### 9.3 扩展性要求

- 支持水平扩展（多实例部署）
- 消息队列支持负载均衡
- Milvus 支持集群部署

## 十、风险与应对

### 10.1 性能风险

**风险**：每次对话都查询数据库和向量库，可能导致响应变慢

**应对**：
- 用户画像查询结果缓存到 Redis（5分钟）
- 向量检索结果缓存（10分钟）
- 异步化记忆提取流程
- 设置超时机制，超时则降级

### 10.2 准确性风险

**风险**：AI 提取的信息可能不准确，导致错误记忆

**应对**：
- 为每条记忆设置置信度分数
- 低置信度记忆（< 0.7）不传入 AI
- 提供管理后台，允许医生/管理员审核和修正记忆
- 重要医疗信息需要人工验证后才标记为 verified=1

### 10.3 隐私风险

**风险**：用户敏感信息存储在向量数据库中

**应对**：
- 向量数据库部署在内网，不对外暴露
- 敏感信息加密存储
- 定期清理过期记忆（超过6个月未使用）
- 用户可以主动删除自己的记忆

### 10.4 成本风险

**风险**：Embedding API 调用和向量存储成本较高

**应对**：
- 使用通义千问 Embedding API（成本较低）
- 记忆去重，避免重复存储
- 定期清理低价值记忆（置信度低且未被使用）
- 考虑后期自建 Embedding 服务
