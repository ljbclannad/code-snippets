# 项目中数据库读写分离配置分析

## 概述

本项目使用 **ShardingSphere JDBC** 实现数据库读写分离，目前只有 `order-service` 配置了完整的读写分离功能。

---

## 架构拓扑

```
order-service (8081)
    ↓
ShardingSphere JDBC
    ↓
┌─────────────────────────────────────┐
│  读写分离 + 分表组合                  │
├─────────────────────────────────────┤
│  写操作 → master (3306)              │
│           ├→ t_order_0               │
│           └→ t_order_1               │
│                                      │
│  读操作 → slave1 (3307) ─┐          │
│           slave2 (3308) ─┤ 轮询      │
│           ├→ t_order_0   │          │
│           └→ t_order_1   │          │
└─────────────────────────────────────┘
```

#### MySQL 配置文件

**主库配置（master.cnf）**：
```ini
[mysqld]
server-id=1                    # 唯一标识
log-bin=mysql-bin              # 开启 binlog
binlog-format=ROW              # ROW 格式（推荐）
expire_logs_days=7             # binlog 保留 7 天
max_binlog_size=100M           # 单个 binlog 文件大小
gtid_mode=ON                   # 启用 GTID
enforce_gtid_consistency=ON    # 强制 GTID 一致性
```

**从库配置（slave1.cnf / slave2.cnf）**：
```ini
[mysqld]

read_only=1                    # 只读模式（防止误写）
gtid_mode=ON                   # 启用 GTID
enforce_gtid_consistency=ON    # 强制 GTID 一致性
```

### 2. ShardingSphere 读写分离配置

**配置文件位置**：
`order-service/src/main/java/com/lx/governance/order/config/ShardingSphereDataSourceConfig.java`

#### 核心代码解析

```java
@Configuration
public class ShardingSphereDataSourceConfig {

    @Bean("shardingSphereDataSource")
    @Primary
    public DataSource shardingSphereDataSource() throws SQLException {
        // 1. 创建物理数据源
        Map<String, DataSource> dataSourceMap = new HashMap<>();
        dataSourceMap.put("master", createDataSource(mysqlHost, 3306));
        dataSourceMap.put("slave1", createDataSource(mysqlHost, 3307));
        dataSourceMap.put("slave2", createDataSource(mysqlHost, 3308));

        // 2. 配置读写分离规则
        ReadwriteSplittingDataSourceRuleConfiguration readwriteSplittingGroup = 
            new ReadwriteSplittingDataSourceRuleConfiguration(
                "order_ds",              // 逻辑数据源名称
                "master",                // 写数据源
                Arrays.asList("slave1", "slave2"),  // 读数据源列表
                "round_robin"            // 负载均衡算法
            );

        // 3. 配置负载均衡算法
        Map<String, AlgorithmConfiguration> loadBalancers = new HashMap<>();
        loadBalancers.put("round_robin", 
            new AlgorithmConfiguration("ROUND_ROBIN", new Properties()));

        ReadwriteSplittingRuleConfiguration readwriteSplittingRule = 
            new ReadwriteSplittingRuleConfiguration(
                Collections.singletonList(readwriteSplittingGroup),
                loadBalancers
            );

        // 4. 配置分片规则（基于逻辑数据源）
        ShardingTableRuleConfiguration orderTableRule = 
            new ShardingTableRuleConfiguration(
                "t_order",
                "order_ds.t_order_${0..1}"  // 使用逻辑数据源
            );
        orderTableRule.setTableShardingStrategy(
            new StandardShardingStrategyConfiguration("order_no", "order-inline")
        );

        // 5. 配置分片算法
        Map<String, AlgorithmConfiguration> shardingAlgorithms = new HashMap<>();
        Properties inlineProps = new Properties();
        inlineProps.setProperty("algorithm-expression", 
            "t_order_${Math.abs(order_no.hashCode()) % 2}");
        shardingAlgorithms.put("order-inline", 
            new AlgorithmConfiguration("INLINE", inlineProps));

        ShardingRuleConfiguration shardingRule = new ShardingRuleConfiguration();
        shardingRule.getTables().add(orderTableRule);
        shardingRule.setShardingAlgorithms(shardingAlgorithms);

        // 6. 启用 SQL 日志
        Properties props = new Properties();
        props.setProperty("sql-show", "true");

        // 7. 创建 ShardingSphere 数据源
        return ShardingSphereDataSourceFactory.createDataSource(
            dataSourceMap,
            Arrays.asList(readwriteSplittingRule, shardingRule),
            props
        );
    }

    private DataSource createDataSource(String host, int port) {
        HikariDataSource ds = new HikariDataSource();
        ds.setDriverClassName("com.mysql.cj.jdbc.Driver");
        ds.setJdbcUrl(String.format(
            "jdbc:mysql://%s:%d/order_db?useSSL=false&useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true",
            host, port));
        ds.setUsername(mysqlUser);
        ds.setPassword(mysqlPass);
        // 主库连接池较小（写操作少），从库连接池较大（读操作多）
        ds.setMaximumPoolSize(port == 3306 ? 20 : 50);
        return ds;
    }
}
```

## 查询如何路由到从库

### 1. 路由规则

ShardingSphere 根据 SQL 类型自动路由：

| SQL 类型 | 路由目标 | 说明 |
|----------|----------|------|
| **SELECT** | slave1 / slave2 | 轮询负载均衡 |
| **INSERT** | master | 写操作 |
| **UPDATE** | master | 写操作 |
| **DELETE** | master | 写操作 |

### 2. 负载均衡算法

**ROUND_ROBIN（轮询）**：
```
第1次查询 → slave1
第2次查询 → slave2
第3次查询 → slave1
第4次查询 → slave2
...
```

**配置代码**：
```java
loadBalancers.put("round_robin", 
    new AlgorithmConfiguration("ROUND_ROBIN", new Properties()));
```

### 3. 路由流程

```
1. 应用层执行 SQL：SELECT * FROM t_order WHERE order_no = 'xxx'
   ↓
2. ShardingSphere 拦截 SQL
   ↓
3. 判断 SQL 类型：SELECT（读操作）
   ↓
4. 应用读写分离规则：路由到 slave1 或 slave2
   ↓
5. 应用分片规则：根据 order_no 哈希到 t_order_0 或 t_order_1
   ↓
6. 执行实际 SQL：slave1 ::: SELECT * FROM t_order_0 WHERE order_no = 'xxx'
   ↓
7. 返回结果
```

### 4. SQL 日志示例

**读操作（路由到从库）**：
```log
Logic SQL: SELECT * FROM t_order WHERE order_no = 'ORDER-001'
Actual SQL: slave1 ::: SELECT * FROM t_order_0 WHERE order_no = 'ORDER-001'
```

**写操作（路由到主库）**：
```log
Logic SQL: INSERT INTO t_order (order_no, user_id, ...) VALUES (?, ?, ...)
Actual SQL: master ::: INSERT INTO t_order_1 (order_no, user_id, ...) VALUES (?, ?, ...)
```

## 特殊场景处理

### 1. 事务内的查询

**规则**：事务内的所有操作（包括 SELECT）都路由到主库

**原因**：避免主从延迟导致的数据不一致

**示例**：
```java
@Transactional
public void createOrder(OrderRequest request) {
    // 1. 插入订单（master）
    orderMapper.insert(order);
    
    // 2. 查询订单（也走 master，不走 slave）
    Order savedOrder = orderMapper.selectByOrderNo(order.getOrderNo());
    
    // 3. 更新库存（master）
    inventoryClient.deduct(request.getProductId(), request.getQuantity());
}
```

**SQL 日志**：
```log
Logic SQL: SELECT * FROM t_order WHERE order_no = 'ORDER-001'
Actual SQL: master ::: SELECT * FROM t_order_0 WHERE order_no = 'ORDER-001'
```

### 2. Seata 分布式事务

**规则**：`@GlobalTransactional` 内的所有操作都路由到主库

**示例**：
```java
@GlobalTransactional
public void createOrder(OrderRequest request) {
    // 所有操作都走 master
    orderMapper.insert(order);
    inventoryClient.deduct(...);  // 远程调用也走 master
    paymentClient.prepare(...);   // 远程调用也走 master
}
```

**原理**：ShardingSphere 自动检测 Seata 事务上下文，强制路由到主库

### 3. 从库故障降级

**规则**：从库不可用时，自动降级到主库或其他可用从库

**场景**：
```bash
# 停止 slave1
docker stop gov-mysql-slave1

# 查询操作自动降级到 slave2 或 master
curl http://localhost:8080/api/order/ORDER-001
# 请求成功，应用无感知
```

**SQL 日志**：
```log
# slave1 不可用，自动路由到 slave2
Actual SQL: slave2 ::: SELECT * FROM t_order_0 WHERE order_no = 'ORDER-001'
```

## 连接池配置

### 主库连接池（写操作少）

```java
ds.setMaximumPoolSize(20);  // 最大连接数
ds.setMinimumIdle(5);       // 最小空闲连接
```

### 从库连接池（读操作多）

```java
ds.setMaximumPoolSize(50);  // 最大连接数
ds.setMinimumIdle(10);      // 最小空闲连接
```

**设计原因**：
- 写操作通常较少，主库不需要太多连接
- 读操作通常较多，从库需要更多连接来支撑高并发查询

## 主从复制原理

### 1. 复制流程

```
Master (3306)
    ↓ binlog (ROW格式)
    ├→ Slave1 (3307)
    │   ↓ IO Thread 读取 binlog
    │   ↓ 写入 Relay Log
    │   ↓ SQL Thread 应用到本地
    │
    └→ Slave2 (3308)
        ↓ IO Thread 读取 binlog
        ↓ 写入 Relay Log
        ↓ SQL Thread 应用到本地
```

### 2. GTID 模式

**GTID（Global Transaction Identifier）**：全局事务标识符

**优势**：
- 每个事务有唯一的 GTID
- 从库故障恢复时，自动定位到正确的 binlog 位置
- 简化主从切换流程

**配置**：
```ini
gtid_mode=ON
enforce_gtid_consistency=ON
```

### 3. 主从延迟

**正常情况**：延迟 < 1s（局域网环境）

**监控指标**：
```sql
SHOW SLAVE STATUS\G

-- 关键指标：
Slave_IO_Running: Yes          -- IO 线程正常
Slave_SQL_Running: Yes         -- SQL 线程正常
Seconds_Behind_Master: 0       -- 主从延迟（秒）
```

## 总结

### ✅ 已实现的服务

| 服务 | 读写分离 | 分片 | 负载均衡 |
|------|----------|------|----------|
| **order-service** | ✅ | ✅ | ROUND_ROBIN |
| payment-service | ❌ | ✅ | - |
| user-service | ❌ | ✅ | - |
| inventory-service | ❌ | ❌ | - |
| appointment-service | ❌ | ❌ | - |

### 核心要点

1. **查询路由到从库的关键**：
   - ShardingSphere 自动识别 SELECT 语句
   - 根据负载均衡算法（ROUND_ROBIN）轮询路由到 slave1 或 slave2
   - 无需在代码中显式指定

2. **逻辑数据源**：
   - `order_ds` 封装了 master + slave1 + slave2
   - 分片规则引用逻辑数据源，而不是物理数据源
   - ShardingSphere 自动处理读写路由 + 分片路由

3. **事务一致性**：
   - `@Transactional` 或 `@GlobalTransactional` 内的所有操作强制走主库
   - 无需额外配置，ShardingSphere 自动识别事务上下文

4. **故障降级**：
   - 从库不可用时自动降级到主库或其他可用从库
   - 应用无感知，继续提供服务

5. **连接池优化**：
   - 主库连接池较小（20），写操作少
   - 从库连接池较大（50），读操作多
