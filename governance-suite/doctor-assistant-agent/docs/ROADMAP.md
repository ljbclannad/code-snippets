# 医生助手 Agent 改造优先级路线图

## 1. 文档目标

本文档用于梳理 `doctor-assistant-agent` 从“可运行的医疗 Agent 原型”演进到“边界清晰、风险可控、可持续迭代的医疗 Agent 项目”的改造路线。

适用方式：

- 作为后续分阶段实施的总纲
- 作为需求收敛和优先级讨论的依据
- 作为每一阶段验收时的检查清单

---

## 2. 当前项目判断

当前 `doctor-assistant-agent` 已经具备以下基础：

- 有明确的 ReAct Agent 架构
- 有会话持久化、暂停恢复和审批链路
- 有基础工具系统、风险分级和 API 接口
- 有一定的监控、测试和部署文档

但当前状态更接近：

`能运行的医疗 Agent 原型`

而不是：

`边界明确、评测充分、可上线治理的医疗 Agent`

当前主要缺口集中在：

- 目标场景过宽
- 医疗安全规则不够硬
- 输出结构化不足
- 审计链路不完整
- 文档与代码实现存在漂移
- 缺少医疗场景评测体系

---

## 3. 改造原则

后续改造遵循以下原则：

1. 先收敛场景，再扩展能力  
   不先做泛化医生助手，先把单一医疗场景做深做稳。

2. 先补安全边界，再补模型能力  
   医疗 Agent 的第一优先级不是“更聪明”，而是“更不容易做错危险决策”。

3. 先做结构化输出，再做复杂工作台  
   先让结果可验证、可审计、可评测，再考虑界面体验。

4. 先建立评测，再持续迭代  
   没有病例评测集，后续优化无法判断是进步还是退步。

5. 尽量复用现有模块  
   优先围绕现有会话、工具、审批、知识检索能力改造，不做无关重构。

---

## 4. 总体阶段划分

### P0：先把项目定义和安全边界定住

目标：

- 明确 Agent 服务的单一医疗场景
- 建立硬性的医疗安全约束
- 让输出和审计具备可控性

### P1：把能力、实现和验证体系补齐

目标：

- 让系统能力和文档定义一致
- 让工具、输出、降级策略更可靠
- 建立一套最小可用医疗评测机制

### P2：做长期演进能力和产品化增强

目标：

- 提升知识治理、长期患者视图、监控和合规能力
- 为更复杂的人机协同和真实使用场景打基础

---

## 5. P0 路线图

### 5.1 P0 目标

把项目从“泛化医生助手原型”改造成“单场景、可控输出、风险可拦截”的医疗 Agent 基线版本。

### 5.2 P0 核心任务

#### 任务 1：场景收敛

将项目目标从泛化“医生助手”收敛到一个明确场景：

`减重管理医生助手`

原因：

- 当前已有患者档案、体重记录、聊天记录、处方历史等数据模型
- 现有 ReAct 工具链与“体重趋势分析 + 随访 + 风险提示”高度契合
- 场景边界清晰，适合作为第一阶段落地场景

交付物：

- 明确项目定位说明
- README 中目标更新为减重管理医生助手
- 工具清单按场景重新分组

验收标准：

- 能用一句话说明系统服务对象、解决问题、适用边界
- 所有后续能力都能围绕“减重管理”解释其必要性

#### 任务 2：医疗安全规则落地

将高风险控制从“主要依赖 prompt”升级为“prompt + 业务规则”的双层控制。

优先补充的规则类型：

- 急症关键词或症状拦截
- 危险行为或心理高危信号识别
- 信息不足时禁止输出确定性建议
- 必须转人工或建议线下就医的触发条件
- 高风险建议必须走审批链路

当前第一版已落地的减重管理安全规则：

- 目标预检：识别胸痛、呼吸困难、胸闷、心悸、晕厥、自杀等高危信号
- 高风险行动前校验：处方建议和诊断建议前必须已有患者档案或体重趋势证据
- 最终回答兜底：当回答包含高危症状但仍给出继续观察或继续当前方案时，强制降级为转人工和线下就医提示

建议实现方式：

- 新增独立的安全规则模块
- 在 Agent 输出前和高风险工具调用前执行校验
- 对违规情形返回固定结构的安全响应

交付物：

- 医疗安全规则清单
- 规则执行入口
- 安全响应模板

验收标准：

- 对高危输入能稳定拦截
- 对信息不足场景不会输出看似确定的医疗结论
- 高风险建议无法绕过审批链路

#### 任务 3：最终输出结构化

将当前自由文本 `finalAnswer` 升级为结构化结果，建议至少包含：

- 问题摘要
- 关键证据
- 风险判断
- 建议动作
- 是否需要人工介入
- 不确定项

建议目标：

- 便于医生快速查看
- 便于后端审计和前端展示
- 便于后续做自动评测

当前第一版结构化输出字段：

- `summary`
- `keyFindings`
- `riskLevel`
- `recommendedActions`
- `needsAttention`
- `uncertainties`

交付物：

- 结构化响应模型
- Prompt 协议更新
- API 返回示例更新

验收标准：

- 常见场景下返回字段完整
- 输出中能明确区分事实、推断、不确定项

#### 任务 4：补全审计闭环

对中风险和高风险操作建立完整审计信息，而不是只打印日志。

应记录内容：

- 会话 ID
- 医生 ID / 患者 ID
- 工具名称
- 输入参数
- 工具输出
- 触发原因
- 审批状态
- 审批人
- 审批意见
- 时间线

当前第一版已落地的审计能力：

- 高风险待审批任务创建时写入审计日志
- 审批通过或拒绝时回写审计状态和审批意见
- 审计日志已关联会话 ID、任务 ID、工具名、输入参数、审批状态

当前补全后的审计闭环能力：

- 中风险和低风险工具执行结果已写入审计日志
- 高风险任务创建、审批、审批后执行已可追踪
- 最终会话结果（成功、待审批、失败、达到最大步数）已写入审计日志
- 审计日志已覆盖输入、输出、最终状态、审批状态、审批意见、时间信息

交付物：

- 审计表或审计落库逻辑
- 查询接口或内部查询能力
- 审计字段定义

验收标准：

- 任一中高风险操作都可追踪
- 能复原一次高风险建议的产生和审批过程

### 5.3 P0 完成标志

满足以下条件即可视为 P0 完成：

- 项目场景已收敛
- 医疗安全规则已代码化
- 最终输出结构化
- 中高风险审计闭环可追踪

---

## 6. P1 路线图

### 6.1 P1 目标

在 P0 的安全和边界基础上，补齐能力定义、实现一致性、异常降级和最小评测体系。

### 6.2 P1 核心任务

#### 任务 1：按场景重构工具能力

围绕收敛后的目标场景，对工具进行清理、保留、补强。

建议方向：

- 保留和场景强相关工具
- 下线或降权暂时无用的泛化工具
- 补充场景关键缺失工具

如果定位为减重管理，建议优先保留：

- 患者档案
- 体重历史
- 聊天历史
- 处方历史
- 健康知识检索
- 随访任务创建

交付物：

- 新版工具清单
- 工具说明和风险分级
- 工具输入输出约束文档

验收标准：

- 每个工具都能解释其业务必要性
- 工具集合与目标场景强相关

#### 任务 2：增强证据链

要求 Agent 的每个重要建议都具备可追溯证据，而不是只给结论。

建议补充：

- 建议所依据的 Observation 列表
- 引用的知识来源摘要
- 模型推断与已知事实的区分
- 高风险建议的证据充分性要求

交付物：

- 证据字段设计
- 输出模板更新
- 高风险建议证据校验规则

验收标准：

- 高风险建议可被复盘
- 医生能够快速知道“为什么这么建议”

#### 任务 3：完善降级策略

系统需要在异常情况下做可预期的退化，而不是简单失败。

重点场景：

- 工具超时
- 工具返回空数据
- 向量检索不可用
- 模型协议错误
- 多次重试失败

建议目标：

- 优先返回保守结果
- 必要时提示人工接管
- 避免在不可靠状态下给出强建议

交付物：

- 异常场景矩阵
- 降级处理逻辑
- 降级返回规范

验收标准：

- 关键依赖异常时系统行为可预测
- 不会因局部故障输出高风险错误建议

#### 任务 4：建立评测集 V1

建立第一版医疗场景评测集，用于验证系统改造是否真的提升质量。

建议覆盖：

- 正常随访场景
- 信息不足场景
- 高危信号场景
- 需要审批场景
- 应拒答或转人工场景
- 工具异常场景

建议规模：

20 到 50 条高质量样例

交付物：

- 评测样本
- 期望输出标准
- 简单自动化评测脚本或半自动评测流程

验收标准：

- 每次关键改动后可回归评测
- 能识别明显的安全退化和行为回归

#### 任务 5：统一文档与实现

当前 README、配置说明、工具清单与实际代码已有漂移，P1 需要统一：

- README 中的模型配置说明
- README 中的工具列表
- API 文档中的请求/响应示例
- 设计文档中的能力边界

交付物：

- 更新后的 README
- 更新后的 API 文档
- 场景化后的能力说明

验收标准：

- 文档描述与代码行为一致
- 新成员仅通过文档即可正确理解系统能力

### 6.3 P1 完成标志

满足以下条件即可视为 P1 完成：

- 文档与实现一致
- 工具体系已按场景重构
- 输出具备证据链
- 降级策略明确
- 评测集 V1 可用

---

## 7. P2 路线图

### 7.1 P2 目标

补齐长期演进所需的知识治理、长期记忆、监控、协同和合规能力。

### 7.2 P2 核心任务

#### 任务 1：医疗知识治理

为知识来源建立分层与治理机制。

建议来源层次：

- 临床指南
- 医院内部规范
- 患教内容
- 病例库 / 相似病例

建议补充字段：

- 来源类型
- 更新时间
- 可信等级
- 适用范围

交付物：

- 知识来源模型
- 知识入库规范
- 检索结果可信度说明

#### 任务 2：患者长期画像与纵向记忆

将当前“会话状态持久化”升级为“患者长期视图”。

建议维度：

- 长期风险趋势
- 依从性标签
- 历史干预效果
- 多次随访中的重复问题

交付物：

- 患者纵向画像设计
- 长期记忆字段或聚合逻辑
- 画像更新策略

#### 任务 3：医疗专属监控指标

在已有执行监控基础上补充医疗向指标。

建议指标：

- 高危拦截率
- 转人工率
- 审批命中率
- 审批驳回率
- 知识库命中率
- 工具异常率
- 拒答率

交付物：

- 指标定义
- 监控埋点
- Dashboard 更新

#### 任务 4：人机协同工作台增强

围绕医生使用流程增强工作台表达能力。

建议能力：

- 风险等级展示
- 证据摘要展示
- 审批入口
- 关键时间线
- 历史建议对比

交付物：

- 工作台需求定义
- API 支撑字段
- 交互原型或页面实现

#### 任务 5：合规和脱敏能力

为未来更真实的数据使用场景补齐基本合规能力。

建议方向：

- 敏感字段脱敏
- 日志最小化
- 数据保留策略
- 访问权限控制

交付物：

- 脱敏策略
- 日志规范
- 权限与保留规则说明

### 7.3 P2 完成标志

满足以下条件即可视为 P2 完成：

- 知识来源具备治理能力
- 患者有长期画像和趋势视图
- 医疗专属监控指标可观测
- 医生协同链路更完整
- 基本合规能力具备

---

## 8. 推荐实施顺序

建议按以下节奏推进：

### 阶段一

只做 P0。

原因：

- 不先定边界，越往后改动成本越高
- 医疗安全规则必须先落地

### 阶段二

在 P0 完成后做 P1。

原因：

- 先把能力定义和系统行为收口
- 再建立回归验证机制

### 阶段三

在 P1 稳定后做 P2。

原因：

- P2 是增强项，不适合作为第一阶段阻塞项
- 需要在前两阶段稳定后逐步引入

---

## 9. 建议的下一步

后续建议严格按顺序推进，不跳级：

1. 先确定最终收敛场景
2. 再设计 P0 的安全规则和结构化输出
3. 然后逐项实施 P0
4. P0 完成后再规划 P1 的评测和工具重构

如果后续进入实施阶段，建议每次只执行一个明确子任务，例如：

- 先只做“场景收敛”
- 再只做“医疗安全规则”
- 再只做“结构化输出”

这样可以减少一次性改动过多带来的不确定性。
